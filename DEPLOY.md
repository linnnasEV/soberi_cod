# Публикация на Yandex Cloud

Сайт переезжает с GitHub Pages на российский хостинг — Yandex Object Storage.
Для «СобериКод» это не просто смена адреса: заявленное в описании проекта
импортозамещение перестаёт быть словами, если платформа лежит на зарубежной площадке.

## Что проверено заранее

- **HTTPS работает сразу**, без своего домена и без CDN: адрес вида
  `https://<бакет>.website.yandexcloud.net` закрыт сертификатом GlobalSign
  (`*.website.yandexcloud.net` входит в сертификат). Это критично — без HTTPS
  браузер не запустит сервис-воркер, и офлайн-режим платформы просто не включится.
- **Имя бакета не должно содержать точек.** Сертификат покрывает только один уровень:
  `sobericod` — да, `soberi.cod` — нет, и сайт откроется с ошибкой безопасности.
- **Бесплатного уровня хватает с запасом.** Сайт весит 250 КБ при лимите 1 ГБ;
  бесплатно отдаётся 100 ГБ трафика и 100 000 запросов GET в месяц.
  Это примерно 400 000 открытий сайта в месяц — столько школ в проекте не будет.
- **CDN подключать не нужно** и не стоит: он платный с первого гигабайта,
  а выигрыша для статики в 250 КБ не даст.

## Шаги, которые нужно сделать вручную

Это единственная часть, которую нельзя автоматизировать: нужен вход в аккаунт.
Названия пунктов меню — как в консоли Yandex Cloud.

### 1. Аккаунт и платёжный аккаунт

Зарегистрироваться на [console.yandex.cloud](https://console.yandex.cloud) через
Яндекс ID и создать платёжный аккаунт. Карту привязать придётся — без платёжного
аккаунта ресурсы не создаются. Списаний за этот сайт не будет: он целиком
укладывается в бесплатный уровень, а новым пользователям ещё дают стартовый грант.

### 2. Бакет

**Object Storage** → **«Создать бакет»**:

- **Имя:** `sobericod`. Без точек — иначе HTTPS не заработает. Имя уникально
  на весь Yandex Cloud, так что если занято — `sobericod-school`, `soberikod-edu`.
- **Публичный доступ:** «Чтение объектов» и «Чтение списка объектов» → **«Для всех»**.
  Без этого хостинг просто не включится.
- **Класс хранилища:** «Стандартное».
- Максимальный размер и шифрование не трогать: шифрование несовместимо с хостингом.

Если доступ забыли открыть при создании — бакет → **Настройки** → вкладка
**«Основные»** → те же два поля → **«Сохранить»**.

### 3. Включить хостинг

Бакет → **Настройки** → вкладка **«Веб-сайт»** → режим **«Хостинг»**:

- **Главная страница:** `index.html`
- **Страница ошибки:** `index.html`
- **«Сохранить»**

Готовый адрес появится там же, в поле **«Ссылка»**.

### 4. Сервисный аккаунт для загрузки

**Identity and Access Management** → **«Сервисные аккаунты»** → создать:

- имя: `site-deployer`
- роль: **`storage.uploader`**

Именно `storage.uploader`, а не `storage.admin`: этой роли хватает, чтобы заливать
файлы, и не хватает, чтобы что-нибудь сломать. Ключ будет лежать в GitHub, поэтому
прав у него должно быть ровно столько, сколько нужно.

Затем на странице этого сервисного аккаунта: **«Создать новый ключ»** →
**«Создать статический ключ доступа»** → описание (например, `github deploy`) →
**«Создать»**.

Появятся два значения — **идентификатор ключа** и **секретный ключ**.
**Секретный ключ показывается один раз**: закроете окно — восстановить нельзя,
придётся создавать новый. Скопируйте оба сразу.

### 5. Секреты в GitHub

Репозиторий → **Settings** → **Secrets and variables** → **Actions** →
**«New repository secret»**, три раза:

| Name | Secret |
|---|---|
| `YC_BUCKET` | имя бакета, например `sobericod` |
| `YC_ACCESS_KEY_ID` | идентификатор статического ключа |
| `YC_SECRET_ACCESS_KEY` | секретный ключ |

Секреты не видны никому, включая вас, после сохранения — это нормально.

### 6. Запуск

После этого `.github/workflows/deploy.yml` заливает сайт при каждом пуше в `main`.
Первый запуск можно сделать руками: вкладка **Actions** →
«Deploy to Yandex Object Storage» → **«Run workflow»**.

Последним шагом workflow сам открывает сайт и падает, если тот не ответил 200 —
так что молчаливой поломки не будет.

## Если GitHub Actions не подходит

Залить те же файлы можно руками: в консоли бакета перетащить в него `index.html`,
`manifest.json`, `icon.svg`, `sw.js` и папки `css/` и `js/`. Единственное, что
нужно проверить после ручной загрузки, — тип содержимого у `.js` и `.css`
(должны быть `text/javascript` и `text/css`, иначе браузер их не применит).

Локально то же самое делается через AWS CLI — Object Storage совместим с S3:

```bash
aws configure set aws_access_key_id <идентификатор>
aws configure set aws_secret_access_key <секрет>
aws s3 cp . s3://sobericod --recursive --endpoint-url https://storage.yandexcloud.net --acl public-read --cache-control no-cache --exclude ".git/*" --exclude ".github/*"
```

## Про кэш

В workflow всем файлам проставляется `Cache-Control: no-cache`. Это осознанно:
офлайн-режим платформы обеспечивает сервис-воркер со своей стратегией
«сначала кэш», а кэш браузера поверх него только мешает — исправленный урок
может не дойти до детей неделями. При 250 КБ перепроверка файлов бесплатна.

Отдельно важно: **`sw.js` нельзя кэшировать надолго ни при каких настройках**.
Если браузер закэширует старый сервис-воркер, обновления сайта перестанут
доходить вообще.

## Переезд на свой домен (потом)

Адрес `sobericod.website.yandexcloud.net` рабочий, но для школ длинноват.
Свой домен в зоне `.ru` стоит ~200–300 ₽ в год. Порядок действий другой:
имя бакета должно **совпадать с доменом** (бакет `soberikod.ru` для домена
`soberikod.ru`), сертификат выпускается в Certificate Manager с проверкой
через DNS, а в DNS домена ставится запись на `website.yandexcloud.net`.
Делать это стоит только когда адрес пойдёт в методички и на раздатки.

## Пока не переключились

GitHub Pages можно не отключать: пусть оба адреса работают параллельно.
Как только Yandex-адрес проверен на реальном компьютере в школе — поменять
ссылку в `README.md` и в описании проекта, и только потом выключать Pages.
